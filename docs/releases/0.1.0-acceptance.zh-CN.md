## 本轮实际修复

- pnpm 在 Linux 使用合法硬链接，旧暂存器误拒绝。现复制为独立私有文件，保留 symlink/路径/预算检查，不修改共享源文件。
- 仅支持 macOS 的服务安装在其他平台写文件后才失败。现提前拒绝自动安装，已写入“不改动 runtime/注册目录”的回归断言。
- 不同 runtime 共用一个用户级服务标签时可能相互停止。安装和卸载先核对服务所属目录；手工 Broker 占用时给出明确恢复步骤。
- launchd bootout 返回后旧 job 可能尚未删除，重复安装偶发 bootstrap error 5。现等待旧服务移除，再注册并检查 Broker 连接。
- 新标签进入清单的固定 1.5 秒窗口过短。现使用有界动作预算，超时/取消不会再创建标签；提示先列出已有标签再恢复。
- Chrome 关闭标签后的撤权事件可能早于关闭确认。现保留调用方取消并接收已验证的关闭确认，避免将成功关闭误报为撤权失败。

## 结论与边界

上述证据足以支持限定 macOS + Chrome 范围的首个 `0.1.0` 正式版。正式版不意味着任意网站、任意模型或无人值守业务都可靠。

首次 Chrome“加载已解压”仍由用户手动确认。自动化使用全新 CFT profile 和测试加载 API；没有声称通过 Chrome 商店安装，也没有绕过日常 Chrome 的安装确认。Edge、完整 Windows/Linux 安装、自动恢复、跨域 iframe 的任意控制、复杂业务网站长期稳定性和 Codex 同机对比继续迭代。

公网补充任务使用 Example Domain 和本项目 GitHub 页面，无登录账户、无外部表单提交。自然语言规划、模型图像理解、付费/破坏性业务与人工接管后自动续接不在这次自动化通过结论内。没有根据这些确定性检查推算真实网站成功率或宣称 Codex 性能持平。

## 复现入口

先完成 `pnpm install` 和 `pnpm build`，再按需要运行：

```sh
pnpm check
pnpm typecheck
pnpm test
pnpm test:package-install
pnpm test:profile-install /absolute/path/to/installed/dsh/lib/bin.js
DSH_CHROME_TEST_EXECUTABLE="/absolute/path/to/Chrome for Testing" pnpm test:installation /absolute/path/to/installed/dsh-host
```

完整安装验收会使用真实用户级 launchd 测试服务。如果已有本插件后台服务在运行，脚本直接拒绝测试，不会停止日常服务。测试使用临时 plist、运行目录及浏览器 profile；没有调用模型。脚本要求提供能解析 DSH 服务包的已安装宿主目录。
